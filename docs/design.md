# 原生面板设计（方案一）

HA 只当数据源，面板全部由程序用 WinUI 原生控件画。本文是设计，进度和待办在 `plan.md`，取舍理由在 `decisions.md`。

控件规则照抄 HA 自己的判断逻辑，依据是 HA 2026.9 核心源码（各实体类型的 `*EntityFeature` 功能位、`services.yaml`）和前端 20260826.7 源码（`src/data/*.ts`、`src/dialogs/more-info/controls`、`src/panels/lovelace/card-features`）。HA 给某个实体显示什么控件，面板就显示什么控件，不按集成或型号写特例。

## 1. 分界线

| HA 决定 | 程序决定 |
|---|---|
| 有哪些房间、房间顺序（区域和区域排序） | 窗口、顶栏、卡片样式、布局、动画 |
| 主界面放哪些实体（打了标签的实体） | 按实体类型和功能位选控件（照 HA 的规则） |
| 房间温湿度用哪个传感器（区域设置里的「温度传感器」「湿度传感器」） | 主界面里实体分组的先后 |
| 实体名字、图标、所在房间、是否隐藏 | 默认房间、面板尺寸、开机启动、界面语言 |
| 状态文字的翻译（HA 的翻译接口） | |

程序不读写 HA 仪表盘，不嵌 HA 网页，只用 HA 的 WebSocket 接口。

## 2. 数据层

### 连接后取的数据

| 接口 | 用途 |
|---|---|
| `auth`（长期访问令牌） | 登录。令牌按当前 Windows 用户加密保存（DPAPI） |
| `config/area_registry/list` | 区域：名字、图标、顺序、`temperature_entity_id`、`humidity_entity_id` |
| `config/floor_registry/list` | 楼层（下拉菜单里按楼层分组；没有楼层就不分组） |
| `config/device_registry/list` | 设备：名字（`name_by_user` 优先）、区域、型号 |
| `config/entity_registry/list` | 实体：名字、图标、区域、标签、`entity_category`、`hidden_by`、`disabled_by`、`translation_key`、`platform`、`options`（显示精度等） |
| `config/label_registry/list` | 标签名到标签 ID |
| `get_services` | 判断某个类型有没有 `turn_on` / `turn_off`（兜底开关要用） |
| `subscribe_entities` | 全部实体的状态和属性，之后推增量（HA 前端自己就用这个） |
| `frontend/get_translations` | 状态文字的翻译：分类 `entity_component`（按类型），`entity`（按集成，用 `translation_key`） |
| `frontend/get_icons` | 图标规则：分类 `entity_component`、`entity` |
| `subscribe_events` | `area_registry_updated`、`device_registry_updated`、`entity_registry_updated`、`label_registry_updated`、`floor_registry_updated`，收到就重取对应列表 |
| `call_service` | 所有控制 |

断线自动重连；重连后全部重取。

### 实体模型

每个实体合成一份：注册表条目 + 当前状态 + 设备 + 区域。派生字段：

- **类型**：`entity_id` 点号前的部分。
- **区域**：实体自己的区域，没有就用设备的区域（和 HA 的 `getEntityAreaId` 一样）。
- **功能位**：`supported_features`，按位判断。
- **能力**：`min_temp`、`fan_modes`、`options`、`supported_color_modes` 等，以状态属性为准。注册表里的 `capabilities` 是同一份数据的副本。
- **显示名**：照 HA 的 `computeEntityName`：
  - 取实体名，没有就用原始名；
  - 和设备名相同时只显示设备名；
  - 实体名以设备名开头时，去掉这段前缀（后面跟空格、`: `、` - ` 才算）；
  - 程序另外去掉首尾空白，有的集成会给原始名带前导空格。
  - 在设备分组里只显示实体那半截；在主界面显示「设备 实体」。改名在 HA 里改。
- **图标**：照 HA 的 `entityIcon`，按下面的顺序取第一个有的：
  1. 注册表里设的图标；
  2. 状态属性 `icon`；
  3. 集成的图标规则（`get_icons` `entity`，按 `translation_key`，再按状态或数值区间匹配）；
  4. 类型的图标规则（`get_icons` `entity_component`，按 `device_class` 和状态匹配）；
  5. 类型默认图标。

  图标名是 mdi 的，程序内置 Material Design Icons 字体（Apache-2.0，和 MIT 兼容，要带上许可说明）。这样在 HA 里换图标，面板跟着换。
- **状态文字**：照 HA 的 `computeStateDisplay`：
  - `unknown` 和 `unavailable` 用 HA 的通用翻译；
  - 数值按注册表的显示精度格式化，带单位；
  - 时间戳显示成本地时间，时长按时长格式；
  - 其余按顺序查翻译：集成的 `translation_key`、类型的 `device_class`、类型的通用翻译，都没有就显示原文。
- **是否「开着」**：照 HA 的 `stateActive`，决定卡片高亮。例如 `cover` 不是 `closed`、`lock` 不是 `locked`、`media_player` 不是 `standby`，都算开着；按钮、场景、事件这类只要可用就算。
- **不可用**：`unavailable` 时控件全部禁用、卡片变灰，和 HA 一样只看这一个值。

### 演示模式

`--demo` 用内置的假数据，每种类型、主要的功能位组合都有一个样例，不含任何真实家庭数据。界面开发和自测都用它。

## 3. 面板结构

固定尺寸，默认 400 × 640，在设置里改。内容超出时在面板里滚动，窗口高度不变。

2026-10-18 用户点过可交互原型后确认了下面的布局和操作逻辑。

```
┌──────────────────────────────┐
│ 房间名 ⌄                    ☆ │  顶栏：房间下拉 + 默认房间星标
│ [24.4°] [54%] [有人]          │  环境胶囊：每行 3 个，等宽
│ [26.6°] [17%] [还有 5 个 ⌄]   │  超过 3 个时先显示 2 个，加「还有 N 个」
│ 灯光                          │  分组标题
│ ┌──────────┐ ┌──────────┐    │
│ │(●) 吸顶灯 ›│ │(●) 台灯  ›│   │  灯：两列，磁贴里有亮度条
│ │ ━━━━━━○──│ │ ━━━○─────│    │
│ └──────────┘ └──────────┘    │
│ 气候                          │
│ ┌──────────────────────────┐ │
│ │(●) 空调 制冷·室温24°  − 24° +│ │  空调：整行，温度 ±
│ │ [模式 ⌄] [风速 ⌄] [摆风 ⌄]  │ │  三个下拉框
│ └──────────────────────────┘ │
│ ┌ 更多设备        111 个实体 › ┐ │  进二级页
└──────────────────────────────┘
```

### 主界面

- **房间下拉**：列出 HA 的全部区域，按 HA 的区域顺序；有楼层时按楼层分段。最后单独一段是「未分配区域」，放没有区域的实体。空房间照样列出。默认房间在菜单里带一颗星。
- **星标**：把当前房间设为默认房间（存在本机）。星标亮起表示当前房间就是默认房间。
- **环境胶囊**：
  - 先放区域设置里指定的温度、湿度传感器，再放这个房间里打了标签的 `sensor` / `binary_sensor`；
  - 每个胶囊显示图标、读数，下面一行小字是来源（设备名，没有设备时用实体名），悬停显示全名；
  - 每行 3 个，等宽。不做横向滚动：横向滚动看不出后面还有东西。
  - 收起时只显示固定的胶囊（编辑模式里点图钉），其余收进「还有 N 个」，点开全部显示，再点收起。显示几个由用户固定几个决定。
  - 房间里一个都没固定时：超过 3 个就先显示前 2 个，第 3 格是「还有 N 个」。
- **磁贴**：这个房间里打了标签的其他实体，按分组排。分组顺序沿用 HA 区域视图：灯光 → 窗帘 → 气候（空调、除湿/加湿、风扇/新风、热水器）→ 媒体 → 安防（锁、警报、摄像头）→ 场景和脚本 → 其他。同组内按名字排。
  - **同一个设备的多个实体合成一张设备卡**：卡头是设备图标和设备名，下面每个实体一行，右边是它的控件（开关、下拉框、「按一下」按钮、读数）。
  - 只有一个主动作的实体（灯、开关、场景等）用半宽磁贴，两列排；带快捷控件的（空调、风扇、除湿机、设备卡等）占整行。
  - 磁贴的组成：左边是图标按钮，中间是名字和状态文字，右边是 ›（或者 ± 调节器）。下面一行放快捷控件（见第 4 节）。
- **更多设备**：主界面最后一张导航卡，写明这个房间有多少个实体，点了进二级页。
- **空状态**：
  - 房间里没有设备时，写「这个房间还没有设备。在 Home Assistant 里把设备分到这个区域后，会出现在这里。」
  - 有设备、但没有实体打标签时，写「这个房间里还没有实体打上「托盘」标签。在「更多设备」里点实体前面的星标，就能放到这里。」

### 更多设备（二级页）

- 这个房间在 HA 里的全部实体，按设备分组，每个设备一张可折叠的卡片，默认折叠。卡头是设备图标、设备名和实体数。
- 展开后的顺序：
  1. 普通实体；
  2. HA 标成「配置」的，放在「设置」小节；
  3. 标成「诊断」的，放在「诊断」小节。
- 每个实体一行：
  - 最前面是星标，空心表示没上主界面，实心表示已经在主界面上，点一下切换（改 HA 里这个实体的标签）；
  - 然后是名字；
  - 右边是状态文字，能控制的就是控件。
- 不属于任何设备的实体放在最后的「其他」组。
- 在 HA 里隐藏或停用的实体不显示，这是在 HA 里做的决定。停用的实体本来也没有状态。

### 详情页（二级页）

- 一个实体的全部控件，相当于 HA 的「更多信息」对话框：顶部是大号图标按钮、名字和状态，下面按第 4 节列出全部控件，比磁贴上的大。
- 空调的详情页：模式、风速、摆风用分段按钮，目标温度用大号 ±。状态行的室温：空调自己报的当前温度；空调报不出时，显示 HA 区域设置里的「温度传感器」，没设就不显示，程序不替用户挑。这个传感器也能在空调的「磁贴设置」里选，写回同一处。

### 二级页的进出

- 进二级页时，顶栏换成返回按钮加页面标题（「客厅 · 更多设备」或实体名），没有星标。
- 左上角返回、按 Esc、面板收起，都会回到房间主界面。
- 窗口尺寸始终不变。

### 操作逻辑

| 操作 | 结果 |
|---|---|
| 左键点托盘图标 | 弹出面板，总是显示默认房间的主界面；点别处就收起 |
| 从下拉选房间 | 只换内容，窗口大小不变，滚回顶部 |
| 点磁贴的图标按钮 | 执行主动作（见第 4 节）。图标进入「等待中」（闪烁），等 HA 推回新状态才变；程序不自己先改状态。5 秒内没等到就恢复原样，状态行写「没有响应」 |
| 点磁贴的名字或 › | 进这个实体的详情页 |
| 拖亮度条或其他滑块 | 拖动时只改显示的数字，松手才发命令。灯关着时拖动，松手后开灯并调到这个亮度 |
| 按 − / + | 数字马上变，停手 1 秒后才发一次命令，连按只算一次 |
| 选下拉框、点分段按钮 | 立刻发命令 |
| 点「按一下」 | 立刻发 `press`，不确认（HA 也不确认） |
| 不可用的实体 | 变灰，不能点 |
| 和 HA 断开 | 顶栏下面出提示条，控件都不能点，数据保留最后一次的值 |

## 4. 各类型的控件

磁贴列只写快捷控件，详情页列写全部控件。条件里的功能位名字就是 HA 源码里的 `*EntityFeature` 成员。

### 4.1 完整支持

| 类型 | 主动作 | 磁贴快捷控件 | 详情页 |
|---|---|---|---|

### 4.2 只显示状态

`camera`、`image`（第二期再看要不要显示快照）、`device_tracker`、`person`、`sun`、`zone`、`todo`、`calendar`、`notify`、`tts`、`stt`、`conversation`、`ai_task`、`assist_satellite`、`wake_word`、`image_processing`、`geo_location`、`air_quality`、`group` 等：只显示图标、名字和状态文字。

### 4.3 兜底

不认识的类型（以后 HA 新增的类型、自定义集成的类型）：

- 显示图标、名字和状态文字；
- 这个类型在 `get_services` 里同时有 `turn_on` 和 `turn_off`，并且状态是 `on` / `off` 时，加一个开关。这和 HA 的 `canToggleDomain` 一样。

### 4.4 控件和服务

所有控制都走 `call_service`，服务名和参数照 HA 的 `services.yaml`。滑块拖动期间不发命令，松手后再发；连点 ± 时合并成一次（停手 1 秒后发，和 HA 前端调温度、湿度的防抖一样）。发出命令后不改本地状态，等 HA 推回新状态再刷新，避免显示和实际不一致。

## 5. 主界面放什么

- 实体打了指定标签就上主界面，标签名在设置里改，默认「托盘」。
- 打标签的方式：
  - 在 HA 的实体设置里加标签；
  - 或在面板「更多设备」里点实体前面的星标，程序调 `config/entity_registry/update` 改这个实体的标签，效果和在 HA 里改一样。这个接口要求令牌对应的用户是 HA 管理员（用 `auth/current_user` 的 `is_admin` 判断），不是管理员就不显示星标。
- 标签不存在时，第一次点星标由程序调 `config/label_registry/create` 建标签。
- 房间里没有打标签的实体：主界面只显示环境胶囊和「更多设备」。

### 编辑主界面

2026-10-18 用户点过编辑模式的原型后确认。

**进入和退出**

## 11. Windows 提醒

用户主动订阅指定实体的事件或状态条件。条件保存在 HA 的 `options.ha_tray`，本机只保存接收开关和触发记录。程序不自动订阅全部故障，不按设备合并来源，也不替用户选择电量百分比还是低电量事件。

### 主动订阅

- 托盘菜单和实体详情都有提醒入口。事件实体选择事件类型；枚举实体选择一个或多个目标状态；数值实体选择低于或高于及阈值；二值实体选择 `on` 或 `off`。选项来自 HA，不能按实体名或集成猜测。
- 事件类型读取状态属性，没有时读取注册表 `capabilities.event_types`。事件还可选一个属性及原始值；HA 没有解释时显示原值。
- 同一事件类型可能通过附带属性区分具体情况。可选的属性条件使用 HA 给的属性名和原始值；HA 未提供值的解释时显示原值，复杂判断可在 HA 建辅助实体，不在程序里查品牌规格或写型号分支。
- 不做跨实体、跨来源的去重或合并。每条订阅分别生效，用户同时选了两个来源就按两个订阅处理。
- 每条订阅仍需正确区分首批快照、持续状态和一次新事件：持续满足条件不会因普通更新反复触发；事件类型相同但事件时间变了，属于新事件。这是触发规则，不是来源合并。

### 已有基础与缺口

- `HaSession` 通过 `subscribe_entities` 订阅全部实体。监测不依赖当前房间、主界面标签或胶囊是否展开，诊断实体也可选。
- `ReminderEngine` 自行保存条件结果。普通属性更新不等于新事件，`Presenter.IsActive` 只用于界面高亮。
- `Home` 用首批状态快照和后续增量分开判断。`HaSession.Ready` 仍可能早于首批状态，不能单独当作提醒边界。
- `Entity` 目前只保存 `LastChanged`；它表示状态值变化时间，不表示设备最后在线或最后上报时间。设备长时间数值不变不应据此判定离线。
- 单实例使用 `AppInstance` 转发激活。通知点击在数据就绪后打开实体；没有实体参数时打开提醒窗口。
- 已完成真实设备的只读盘点：服务器注册表、最近入库的状态和枚举元数据，并用现有发布版 `--debug` 的 `dump all` 核对实时内存状态，随后恢复正常启动。还核对了事件参数的规格定义；事件名可能与实际语义不符，原始码也可能超出规格列表，不能凭名字推断。家庭明细只保存在本机 `%LOCALAPPDATA%\HaTray\notification-review.md` 及同目录的盘点 JSON，不进入开源仓库；未读取本机令牌。

### 数据入口与场景清单

以下按 HA 提供的数据语义分类，不按品牌、集成、型号或名字关键字写特例。表中的阈值和持续时间都由用户选择。

| 情况 | 可能的数据来源 | 判断及边界 |
|---|---|---|
| 设备报告低电量 | `binary_sensor`，`device_class=battery`，或 `event` 实体 | 二值类 `on` 表示低电量；事件按新发生的事件触发。用户主动选择来源，历史事件不能当作当前低电量状态。 |
| 电池百分比告急 | `sensor`，`device_class=battery`，单位 `%` | 用户设置阈值和恢复阈值；不能把任何百分比传感器都认成电池。 |
| 电压、电池属性、充电状态 | 电压传感器、设备的 `battery_level` 等属性、`binary_sensor.battery_charging` | 电压无通用低电阈值；正在充电与低电量是两件事。属性可在 HA 转成传感器；是否充电时抑制提醒由用户选择。 |
| 除湿机/污水箱满 | 独立二值传感器、枚举 `sensor`、故障码或设备属性 | HA 没有通用 `tank_full` device class。必须核对实体、异常值及恢复值，不能根据设备类型或名字猜测。 |
| 加湿机/净水箱缺水 | 独立传感器、水位读数、枚举或故障属性 | 与水箱满分开配置；高水位、低水位、水箱取出、水箱未装好也是不同情况。 |
| 水位、耗材余量 | 百分比、体积、高度、剩余寿命或枚举状态 | 由用户指定过高或过低条件；`sensor` 的 `device_class=water` 表示水量，不能直接推断水箱满。 |
| 漏水、烟雾、燃气、CO | 二值类 `moisture`、`smoke`、`gas`、`carbon_monoxide` | `on` 表示检测到；数值含水率或气体浓度属于另一类阈值规则。 |
| 故障、危险、防拆、过热/过冷 | 二值类 `problem`、`safety`、`tamper`、`heat`、`cold` | 这些标准类别的 `on` 有明确异常含义；未知故障枚举和数值代码仍需明确选择。 |
| 设备/网络断开、停电 | 二值类 `connectivity`、`power`，或 `unavailable` | 标准二值类通常是 `off` 表示断开/无电，极性与故障类不同；需持续时间，避免短暂重连刷屏。 |
| 状态未知、长期不上报 | `unknown`、无实体状态、时间戳或集成提供的在线状态 | 不属于同一种故障；默认不作为业务告警，也不能当作恢复。长期不上报需可靠的上报时间来源。 |
| 温湿度、CO₂、颗粒物、功率等越界 | 有单位的数值传感器 | 支持上下限、持续时间和恢复区间；单位转换、无效值及阈值随单位变化要处理。 |
| 门窗未关、门锁异常 | 门窗二值类、`lock` 状态或带属性的 `event` 实体 | 打开/未锁通常不是故障；名称叫异常的事件也可能包含正常开关门。用户选择事件及必要的属性条件，不能按事件名全部当故障。 |
| 安防触发 | `alarm_control_panel` 的 `triggered` 等明确状态 | 布防、撤防、触发不能混为一谈。通知默认只导航；撤防、解锁等操作仍走原有验证。 |
| 运动、有人、门铃、按钮 | 二值类 `motion`、`occupancy` 等，`event` 实体或 HA 事件 | 属于用户选择的活动通知；重复发生可能有相同事件类型，不能只比较文字。事件实体可比较事件时间，纯事件另订阅。 |
| 家电完成、扫地机故障、任务结束 | 状态迁移、枚举、属性或 HA 自动化输出 | `idle` 不一定等于完成，`off` 可能是手动停止；复杂判断应在 HA 完成。 |
| 计时器、日程、待办 | `timer.finished` 等事件、日程或自动化输出 | 单看 `timer` 回到 `idle` 无法区分完成与取消；日历/待办的实体状态也不是完整提醒计划。建议由 HA 生成通知。 |
| 更新、维护提醒 | `update` 实体、维护传感器或 HA 通知 | 可选普通提醒，更新可用不应自动归为紧急故障。 |
| HA 已生成的持久通知 | `persistent_notification/get`、`persistent_notification/subscribe` | 独立入口，不是实体状态；可转发标题、正文、通知 ID，并区分已有、添加、更新、移除。 |
| 既有 `alert` | `alert` 实体或其通知输出 | `on` 表示正在告警，`off` 表示已确认但条件可能仍存在，`idle` 才是未触发；不能把确认当恢复。现有 HA `alert` 开发已冻结，不作为新方案的必需依赖。 |
| 普通通知服务和手机通知 | `notify.*` 服务/实体、移动应用通知 | 不存在可自动收取所有历史消息的统一实体流；现有订阅不会收到每一次发送内容，需要 HA 明确输出到选定入口。 |
| 任意自定义集成 | 实体状态、属性、事件，或 HA 模板/自动化 | 未知语义由用户配置或在 HA 归一化；不承诺自动理解全部未来设备。 |

订阅入口不与主界面标签绑定；可列出全部可见实体，不能只列标准故障类别。隐藏实体按现有可见性规则处理，停用或无数据实体应显示监测不可用。没有注册表条目的 YAML 实体可被监测，但不能把规则写进其注册表选项，需要 HA 辅助实体或另行设计规则存储。

### 单条订阅的触发边界

| 边界 | 建议行为 |
|---|---|
| 首次启用时条件已满足 | 建立基线，不把当前状态或历史事件立即当成新触发。 |
| 首次连接、程序重启、HA 重启、断线重连 | 首批快照建立基线，不重放历史事件，也不把全量同步当成新触发。 |
| 新事件 | 时间戳变化且事件类型、可选属性都匹配时触发。`unknown` 只建立基线，不触发。 |
| 离线期间触发又恢复 | 当前状态无法重建经过；若要求追溯，需 HA 持久通知、历史或专门事件存储。 |
| 普通更新或属性变化 | 重新评估条件，但条件持续满足不重复新建通知；属性本身作为条件时也要处理属性增删。 |
| 阈值附近波动 | 配恢复阈值或滞回；例如低于 15% 触发、达到 20% 恢复只是可选示例，不是默认值。 |
| 持续时间与冷却 | 持续时间在条件连续满足后才触发；冷却限制重复频率。断线或未知期间不能证明条件连续满足，计时需暂停或重建。 |
| 值无效 | `unknown`、`unavailable`、属性缺失、空串、非有限数字和解析失败进入未知，不触发数值越界，也不宣告恢复。HA 数值状态是字符串，应按不依赖界面语言的规则解析。 |
| 故障恢复 | 结束本次异常，移除或更新通知中心里的旧通知；恢复弹窗单独可选，默认不增加一次打扰。再次异常允许再次提醒。 |
| 稍后提醒、确认、关闭通知 | 各自独立：关闭 Windows 通知不等于设备恢复；本机延后不等于确认 HA 告警，确认也不能修改真实传感器。延后到期仅在仍异常时提醒。 |
| 多条主动订阅 | 各自判断、各自通知，不根据设备名、近似语义或时间相近自动关联。 |
| 大量设备同时异常 | 分组、限速和摘要，避免全屋断网或 HA 重启后逐台刷屏；HA 连接故障与设备离线分开。 |
| 多台电脑 | 规则可共用，但本机接收开关、延后和通知记录分别保存；是否只让某台电脑提醒需要明确配置。 |
| 实体改名、迁移、删除 | 显示名变化不生成新异常。触发记录优先使用注册表稳定 ID；实体删除或停用不宣告恢复。 |
| 切换 HA 服务器或演示模式 | 隔离规则和通知历史，撤销旧后端计时任务，防止旧状态触发新服务器的通知；演示默认不发送系统通知。 |
| 修改阈值、语言或规则 | 修改条件后重新评估；语言和名字只影响显示。写入失败须可见，不能看似启用实际未保存。 |

提醒判断独立于窗口和控件。状态条件保存上次匹配结果，事件保存上次事件时间；两者都区分首次快照与后续更新。Windows 通知的标识按 HA 服务器、订阅及触发区分，不能只使用显示名。延后提醒、确认和异常汇总属于后续可选功能，首版不以它们为前提。

### Windows 接入

建议使用 Windows App SDK 的 `AppNotificationManager`，支持非打包桌面程序、本地通知、通知中心和点击激活。无需为本地通知引入云推送；无商店也不意味着不能使用该 API。

- 初始化注册通知处理，事件回到 UI 线程；退出时清理注册资源。检查通知支持和设置，发送失败不能使应用退出。
- 点击通知打开对应实体或异常列表；冷启动时暂存目标，等 HA 数据就绪再导航，目标已删除时给出可见结果。处理激活转发、重复回调和旧通知；不得让现有 Mutex 直接丢弃激活。
- 通知内容使用 HA 名称、区域、状态翻译和当前读数；转发正文按纯文字处理，转义 XML、限制长度，不能假定 HA Markdown 可直接渲染。通知参数不携带令牌，不把任意参数直接当服务调用或外部链接执行。
- 支持通知分组、稳定标签、过期时间、更新和移除；Windows 已接受发送不代表用户已看到。勿扰、关闭横幅、通知设置、锁屏设置和系统策略均可能影响呈现，应用内仍需可查看当前异常。
- 电脑休眠、关机或应用退出时，常驻监测停止；本地通知不提供远程唤醒和离线保障。持续告警判断可放在 HA，桌面恢复连接后核对当前未解决问题。已提交的本地定时通知也不能动态验证设备是否仍异常。
- 官方明确不支持提升权限运行的应用通知，测试须用普通权限。严重故障的分类不能被当成绕过系统通知设置的承诺。
- 项目是 `WindowsPackageType=None`，并依赖系统已安装的 Windows App Runtime 2.5。发布目录不内置运行库；目标电脑没有匹配运行时时程序不能启动。通知注册和点击激活仍需在 LTSC 上实测。
- 验收覆盖 Windows 最低支持版本与 Windows 11 LTSC、x64/ARM64、安装路径变化，以及应用运行中/退出后的通知点击。当前电脑上未发送测试通知；ARM64 也未实测。

### 建议的实现范围

1. 当前发布方式下的 Windows 通知注册、通知中心、更新/移除和冷启动点击仍需普通用户权限实测。当前受限环境会拒绝通知注册；失败显示在提醒窗口，不影响程序继续运行。
2. 真实设备已只读盘点。真实名称与 ID 不进入仓库文档、演示数据或测试样例；无法解释的事件参数保留原值。
3. 第一版已提供事件、枚举、二值和数值订阅，包含本机接收开关、每条启停、恢复阈值和点击定位。没有持续时间、跨来源合并、延后或摘要。
4. HA 持久通知转发、延后提醒和异常汇总仍是后续选项。复杂组合条件、日程和纯总线事件交给 HA 模板或自动化。
5. 实体选择和触发条件优先保存在 HA，本机接收开关及单条订阅的触发记录保存在本机并按服务器隔离。`options.ha_tray` 可承载实体订阅，但当前 `TrayOptions.ToJson()` 和 `SetTrayOptionsAsync` 会重写整个命名空间，扩展时须保留新增字段，避免拖排序、改大小或固定胶囊时擦掉订阅。非管理员应仍能接收已有订阅；编辑遵循 HA 权限。

验收需覆盖：未订阅不通知；同类型的两次新事件各通知一次；事件属性过滤；历史事件快照不重放；数值和枚举的匹配进入/保持/退出/再次进入；未知和断线不伪恢复；阈值波动；重连快照与新触发分开；多条订阅独立；关闭通知不改设备；订阅保存失败；通知点击时实体尚未加载或已经删除。演示数据使用虚构实体覆盖这些情况。
